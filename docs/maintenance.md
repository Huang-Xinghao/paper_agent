# 文档维护约定

文档与代码放在同一分支、同一次 PR 中更新。使用说明回答“怎么完成任务”，技术说明回答“为什么这样实现、接口和边界是什么”，变更记录只保留变化，不重复整份设计。入口为 [docs/README.md](README.md)。

## 每次迭代更新哪里

| 改动 | 同时维护 |
| --- | --- |
| 按钮、入口、操作步骤或错误处理 | 用户使用说明；界面职责变化还更新前端模块文档。 |
| API、字段、数据表、并发和权限 | 技术说明、调用方类型及相应测试。 |
| 内置 Skill 正文或资源 | `skills/release.json` 发布号；版本及资源兼容说明；安装包资源检查。 |
| 运行快照策略或批准条件 | 技术说明、用户可感知行为、旧任务兼容验证。 |
| 新能力/修复/兼容变化 | `CHANGELOG.md` 的本轮条目，明确实现范围和验证限制。 |
| 仅提出方案，尚未实现 | 保存在明确标注“讨论稿”的文档，勿写进当前功能清单。 |

不要求每次新增一份报告，优先修改原模块文档。新模块需要文档时才增加文件，并加入目录。前后端共同的业务契约以本仓技术说明为准，前端文档补组件、状态和界面实现，避免维护两份 API 表。

## 合并前怎样检查

1. 让不了解聊天上下文的读者只看使用说明，能否找到入口、完成一次操作、判断是否生效、知道出错去哪处理？具体步骤必须与当前按钮和行为对应。
2. 技术说明能否回答数据放哪、实际调用链、版本如何固定、失败如何处理，以及哪些还没做？核对源码，不凭历史聊天补事实。
3. 核对相对链接、接口名称、示例字段和适用分支；不提交密钥、账号口令、真实研究快照和测试输出。
4. PR 写明前后端关联改动及检查结果，区分确定性替身、真实模型和线上验证。未测到的能力不要写“已通过”。

仓库根目录 PR 模板会提醒这些内容；它是人工协作提示，没有添加自动 CI 门禁。Git 发布不等于服务部署，发布记录应另写实际部署版本和时间。跨仓分支合并时更新文档链接。

## 参考的开源方法

- [Diátaxis](https://diataxis.fr/) 将教程、操作指南、参考和原理解释分开。当前先保留“操作指南”和“技术说明”两类入口，技术说明中兼顾原理；以后内容增长再拆，避免只有文件很多却难以找到答案。
- [Anthropic doc-coauthoring](https://github.com/anthropics/skills/blob/main/skills/doc-coauthoring/SKILL.md) 的“收集背景、整理结构、检查读者理解”适合写方案和说明。本次借鉴其读者检查方法，依据项目源码核对事实；没有安装新 Skill，也没有强制多轮访谈。
- 2026-11-06 使用 `skills find doc-coauthoring` 查询到官方来源候选，页面显示约 98.1K installs，并读取其正文；这些数值只作选材参考，不代表本项目验收结果。源码及生态会更新，采纳具体建议前应重新核对。

文档与代码一起审阅的做法通常称为 **docs as code**：复用 Git 的变更对比、历史和 PR，不额外建立一套容易不同步的维护入口。当前无需增加文档网站、生成器或常驻服务。
