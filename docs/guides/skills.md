# Skill 管理使用说明

Skill 是 Agent 在某个研究阶段使用的一组工作方法，例如“检查数据泄漏”“明确负结果的含义”。侧边栏 **Skill 管理**（`/skills`）集中管理这些规则。当前工作台的所有项目共享配置，尚不支持给每个项目单独配置。

## 第一次使用：添加自己的检查方法

1. 打开 **Skill 管理 → 创建 Skill**。
2. 填写名称、用途和工作指令。名称便于寻找；用途解释解决什么问题；指令明确检查方法和交付要求。
3. 在“适用阶段”选择“方案修订”，保持启用。未选择阶段也能保存，但不会自动附加到研究流程。
4. 预览后保存。回到项目，提交一次方案修订，开始的新修订任务会加载这条规则。
5. 在运行对话中查看“已加载 Skill”记录，核对实际加载的名称和版本。保存成功只表示规则已保存；加载记录也不表示研究结果已经通过质量验收。

示例指令可以写成：

> 检查方案是否使用预测时点之后的信息。区分可用输入、训练标签和评估数据。发现不确定的关键取舍时，给出具体原因及相关方案部分；不要编造验证结果，也不要自行替用户批准。

选择阶段时，区分“研究精炼”和“方案修订”：前者生成细化提案，后者把人工意见整合为可复审的统一方案。只希望影响人的这一轮修改，应绑定后者。

## 修改何时生效

保存后，**尚未开始的阶段**会在第一次调用模型前固定当时的配置；已经开始的阶段继续使用原版本，包括该阶段的多轮调用和同一运行的重试。

例如一个任务正在研究精炼，你更新了实验规划 Skill：如果实验规划还未开始，它会使用新版本；当前研究精炼不会中途换规则。若正在执行的就是实验规划，这轮仍用旧版。新提交的任务会重新按阶段取配置。

升级前已经保存整任务快照的旧运行保留原策略。判断某次运行到底用了什么，以其加载记录为准，不以管理页当前版本推断。

## 内置发布和我的修改怎样区分

| 页面信息 | 含义 |
| --- | --- |
| 最新内置发布，例如 `1.0.0 · ab12cd34` | 开发者随代码发布的版本号，以及内容指纹的前八位。正文或配套模板变化会改变指纹。 |
| 当前使用：我的定制 `v3` | 你在这个工作台保存的第 3 次修订，不是内置包的第 3 次发布。 |
| 定制基于 | 创建这份定制时采用的内置发布；对应的内置可读资源也保持该基准。 |
| 内置发布版，随更新生效 | 当前跟随开发者发布，没有固定在自己的定制正文上；仍遵循阶段开始时固定版本的规则。 |

开发者更新内置内容后，已有定制不会被覆盖。页面会提示有新发布，可以在 **版本历史 → 内置发布** 查看正文及资源路径，再决定是否采用。这里展示的是当前工作台实际见过的发布，不是完整 Git 历史。

**恢复内置版**会采用当前代码提供的最新内置内容，并重新跟随后续内置更新。原定制仍保存在“我的修改”中，恢复某次历史修改会追加一个新修订号，方便追溯。旧数据若没有记录定制基准，会明确显示未知。

自建 Skill 可停用或删除；内置 Skill 不可删除，流程必需 Skill 还必须保持启用并保留默认阶段。可以定制必需 Skill 的正文，但文字规则不会增加工具权限或跳过专家批准。

## 保存冲突时怎么做

如果两个页面都打开同一版，A 保存成功后，B 再保存会提示已被更新。B 的输入保留在当前编辑页，服务器不会用旧内容覆盖 A。

先“下载草稿”保存自己的内容，再“加载最新版本”，把需要的修改合并回去后保存。加载最新版本会替换编辑内容，有确认提示；当前没有自动合并。不要把浏览器内尚未保存的输入当成已备份的数据。

## 常见问题

- **保存了，为什么 Agent 没使用？** 检查是否启用、是否绑定正确阶段、阶段是否已经开始，再看实际加载记录。
- **绑定越多越好吗？** 每个绑定 Skill 的正文都会进入该阶段上下文。互相矛盾或过长的规则会增加理解负担和调用成本，应保持用途明确。
- **可以上传脚本、安装市场包吗？** 当前管理的是文本规则，可下载 `SKILL.md`；没有 ZIP 包导入、脚本安装或 Skill 商店。
- **换电脑后还在吗？** 定制和历史保存在后端工作台数据库。Git 推送只同步代码和内置包，不同步数据库；迁移工作台时需要另行备份/迁移数据。
- **容量限制是什么？** 每工作台最多 100 个自建 Skill，单正文最多 100000 字符且不超过 128 KiB，保存时每阶段绑定正文合计不超过 256 KiB。
