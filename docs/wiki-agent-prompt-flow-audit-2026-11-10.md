## 结论

- 提示词正文已集中在 `paper_agent/agent/wiki_prompts.py`，调用位置按职责分布，当前不需要再次合并文件。
- 主要提示词问题是阶段职责混杂、审核标准不完整，以及少量语义重复；不是同一片段在一次请求中被重复拼接。

### P1：审核标准与生成字段要求需要拆开

位置：`wiki_prompts.py:86、225、296`。

审核提示词复用了 `Return sections...`、`Return idea...` 等生成字段命令。`REVIEW_TASK` 明确要求将前文规则应用于草稿、最终只返回审核 JSON，因此不能直接断言输出格式一定冲突；但这种组合需要额外解释，阶段边界不清。

同时审核没有接收 `DATASET_CONTRACT`、`IDEA_STRUCTURE_PROMPT`、`EXPERIMENT_PROMPT` 和 `CLASSIFICATION_PROMPT` 的详细标准。它被要求检查独立节点分类，却没有对应的维度定义、标签语言和“实车必须有实际车辆数据”等细则；数据集身份匹配、结构描述深度、实验协议要求也没有完整同步。

建议将内容标准与输出字段契约拆开：生成和修订携带自身字段契约，审核携带适用的完整内容标准和审核 JSON 契约。模块顶部声称审核接收与生成相同内容契约，目前与实际部分复用不完全一致，应同步修正文档说明。

### P2：少量规则可合并，修订阶段应明确不可变字段

- `MECHANISM_PROMPT` 与 `EXTRACTION_PROMPT` 都描述自命名允许/禁止出现的位置，可保留一份规范，提取契约只说明映射字段。
- `IDEA_DIAGRAM_PROMPT` 与 `IDEA_STRUCTURE_PROMPT` 都描述输入、模块、输出、融合和格式。可组织成一份结构标准，分清图和图后说明的职责。
- `REVISION_PROMPT` 复用完整内容契约，其中分类要求包含 metadata，但修订阶段禁止返回或修改 metadata。应明确论文身份和已有 metadata 分类不可变，只修订允许变更的实体。
- `IDEA_DIAGRAM_PROMPT` 要求图紧接 `strcture` 标题，而本地检查要求 `idea.structure` 字段直接以代码围栏开始，标题由写入器添加。建议明确“字段只返回正文，标题由程序生成”，避免模型自行加标题触发修订。

不同独立请求重复携带必要规则是正常的，不能为了降低字符数删去审核所需标准。未实际测量模型 token、费用或质量变化。

## 入库流程与重复工作

当前主链路：全文解析 → 生成 → 本地校验及独立审核 → 必要时修订并复审 → 补充验证 → 写入 Paper / Idea / Experiment → 刷新引用和语义关系 → 重建索引 → 校验落盘结果。

正常情况下，没有其他论文时为生成和审核两次模型请求；存在 1–8 篇其他论文时增加一次关系判断；超过 8 篇时可增加一次候选筛选。修订与复审最多再增加两次。这里未计传输重试；候选为空可能省略关系判断。PDF 解析结果在审核和修订阶段复用，没有发现这条链路为每轮模型请求重新解析 PDF。

### P1：重分析的实验正文可能没有更新（已复现）

位置：`wiki.py:345–351`、`research_wiki.py:1341、1361–1365`。

WikiAgent 调用 `add_experiment` 时未开启 `update_on_exist`；相同 slug 已存在就直接返回。最终检查验证实验文件、分类和关系存在，但不验证实验正文是否与本轮分析一致。

临时目录内连续运行两次相同论文，第二次保持实验标题但替换 `results`：流程成功返回，两个实验文件均保留第一次结果，均不包含第二次结果。Paper 和 Idea 会更新，而同名 Experiment 正文未更新。这是更新一致性问题，应优先于纯提示词压缩处理；修复时需要明确如何保护人工编辑。

### P1：索引与 query pack 多次全量重建（已计数）

位置：`wiki.py:309、325、328、337、345、367–368`；底层各节点写入函数自行重建。

临时目录实测：新论文含 2 个实验时，`rebuild_index` 和 `rebuild_query_pack` **各调用 7 次**；同一论文再次导入时各 3 次。新建路径一般各为 `5 + 实验数` 次。

建议为入库增加批量写入模式，中间写节点时延迟刷新，最后统一重建一次。底层函数仍需支持独立工具/CLI 调用后立即刷新，不能直接全局删除其刷新行为。

### P2：重复写入可合并

| 项目 | 位置 | 判断与建议 |
| --- | --- | --- |
| 草稿 `source.json` | `wiki.py:225`、`wiki_quality.py:413` | 同路径同内容写两次，已动态确认；明确单一写入责任 |
| 新 Idea 正文 | `wiki.py:328–339` | upsert 已写 thesis/structure，随后立即再更新；合并创建与更新入口，保留旧页更新和人工内容保护 |
| 发布 `.quality.json` | `wiki.py:320、402` | 同路径写两次，末次增加最终内容哈希；考虑保留草稿诊断记录、仅最终发布一次 |

草稿来源与公开 `research-wiki/sources/<document_id>.json` 位于不同位置、承担不同生命周期，不认定为可以直接删掉其中之一。

### P2：校验重复、部分校验过晚

位置：`wiki_quality.py:97` 起的 `analysis_errors`；`wiki.py:262–289`。

章节合法性、正文非空、Idea/Experiment 部分结构检查在多个位置实施。数据集目录 ID、分类结构、自命名和书目验证则在独立审核之后执行，不在既有的一次修订闭环内，可能先消耗审核请求再因确定性的错误退出。

建议统一完整的分析预检入口，将适合自动修复的问题纳入既有修订闭环，并在昂贵审核前检查。若让修订处理目录匹配，还需传入原始 dataset catalog；当前修订请求只有 draft、issues、review、source_document。落盘后的内容、分类和图关系验证承担不同职责，应保留。

### P2：全库引用刷新会逐论文重写整张图

位置：`wiki_citations.py:173–193`、`wiki_relations.py:131–148`。

每次导入遍历各篇已存书目，对每个 owner 调用 `write_relations`；该函数每次读取整张图、写临时图并替换。可批量计算各 owner 的引用边，保留手工边和其他来源边，再统一提交一次。

全库重新解析引用本身有必要：新入库论文可能补全旧论文以前未匹配的引用。不能只刷新当前论文，现有“被引论文后到”测试也覆盖了这一需求。

### P3：已有元数据时可能多一次 arXiv 请求

位置：`wiki.py:309–313`、`research_wiki.py:755–772`。

新建带 arXiv ID 的论文时，WikiAgent 已有经校验的 metadata，但没有传底层支持的 `prefetched_meta`，底层仍可能再调用元数据接口。可明确元数据权威性后复用已有结果。本项是静态调用链确认，未发真实网络请求。

## 建议顺序与保留项

1. 修复实验重分析更新缺口，统一预检及审核标准。
2. 合并入库期间的索引刷新、重复写入和引用图批量提交。
3. 精简提示词重叠措辞，明确修订字段边界和标题由谁生成。

独立审核、一次定向修订后的复审、来源证据校验、最终落盘验证，以及新论文到达后补全旧引用，均有独立职责，不建议按冗余直接删除。
