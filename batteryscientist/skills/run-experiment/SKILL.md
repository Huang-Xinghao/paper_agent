# 实验执行检查与故障诊断

由 experiment-bridge 调用，不作为独立 workflow 节点。Manifest 格式统一见 [experiment-bridge 的 Manifest 契约](../experiment-bridge/SKILL.md#manifest-契约)。

## 1. 确认本次执行上下文

- 读取 `refine-logs/EXPERIMENT_PLAN.md` 和 `experiments/manifest.json`，确认本次 jobs 的稳定 ID、所属 D/B 块、入口命令、前置依赖和预期产物。
- 读取 `project-config.json` 中的 `compute`、`execution`，了解设备、线程、并行数、超时和累计预算；未设置的时长上限按运行器默认语义处理。
- 续跑时先查看 `experiment-queue-state.json`、已有执行回执及 `refine-logs/EXPERIMENT_TRACKER.md`，识别已完成、正在运行和待执行的任务。tracker 由运行器生成，仅供查看。

## 2. 运行前检查

首次执行或环境、入口、输入发生变化时，围绕实际调用链检查：

- **输入与路径**：数据、标签、划分、配置及所需 checkpoint 是否存在且可读；相对路径是否从正确工作目录解析；命令参数与脚本接口一致；输出目录可写，不同 jobs 的产物不会互相覆盖。数据位置优先沿用 bridge 已确认的资源登记和 `data-search/DATA_REPORT.md`。
- **Python 与依赖**：使用实际执行环境检查关键包及版本。manifest 中以 `python`、`python3` 开头的命令会被替换为运行器的 Python；不要根据另一个终端的环境判断依赖齐全。
- **设备**：CUDA 任务结合 `nvidia-smi`、当前环境的 PyTorch 检测及必要的小张量运算确认可用；MPS 按对应后端检查。显卡可见、包能导入不代表计算一定可用。设备占用与可调度性按项目配置和队列判断。
- **日志**：训练入口应能留下实际配置、种子、数据规模、设备、训练/验证进度和最终产物位置，便于判断是否在推进；已有 W&B 等记录可辅助查看，新增外部服务不是执行前提。

检查可使用短诊断命令；缺代码、参数接口或产物保存逻辑时，将具体位置交回 bridge 补齐。

## 3. 通过队列执行

准备好 manifest 后调用 `run_experiments()`，训练、评估及后处理 jobs 均交由运行器执行。
运行器统一负责依赖调度、设备、超时、预算和任务记录。manifest 直接调用实验入口，不编写 receipt 包装器、额外预算守护进程、哈希冻结或重复账本。
每次 attempt 的 status.json 和 output.log 是执行记录来源；queue 和 tracker 是派生进度视图。不要另用后台进程启动同一批实验。

脚本遵循运行器分配的 `BATTERYSCIENTIST_DEVICE` 与 `CUDA_VISIBLE_DEVICES`。进程内的 `cuda:0` 可能对应另一张物理卡，不应手动覆盖可见设备来抢占 GPU。
需要显式 CUDA 的任务若设备不可用，应定位环境或资源问题，不能静默改用其他后端。

工具会等待队列执行结束，实验时长不受模型 HTTP 请求超时限制。等待期间以运行器进度事件为准；工具返回或会话恢复后再读取持久化状态和日志。

## 4. 核对启动、进度与完成

按工具返回的实际路径定位本次 attempt：

- `experiment-runs/<attempt>/status.json`：命令、PID、实际资源、起止时间、耗时、退出码和错误信息。
- `experiment-runs/<attempt>/output.log`：入口加载、数据读取、训练/验证进度、checkpoint 保存及异常堆栈。
- `experiment-queue-state.json`：各 job 的调度状态、依赖、分配设备与重试情况。

启动确认结合回执和日志判断：进程是否已启动、是否进入预期阶段、是否使用分配的设备。
进度判断结合日志中的 epoch/step、产物更新时间以及必要的进程状态；首次数据预处理或日志缓冲可能导致暂时无输出，不能仅凭日志安静判定卡死。

完成时同时核对退出状态和 manifest 的 `expected_outputs`：文件存在性、非空要求，以及声明的 JSON/CSV 指标是否为有限数值。
退出码为 0 但产物不合格仍需处理；某个 job 完成也不代表其所属块或整个计划已完成。

## 5. 按错误来源诊断

先读失败 job 的日志末尾和异常上下文，再追踪到入口、输入或资源；避免只转述工具的失败标题。

| 现象 | 检查与处理 |
| --- | --- |
| 路径、文件或参数错误 | 核对实际工作目录、资源登记、配置路径和 argparse 接口；将错误路径或参数交回 bridge 修复。 |
| 缺包、版本或设备初始化失败 | 在实际 Python 环境确认依赖与后端，定位版本冲突、驱动或设备可见性问题。 |
| CUDA OOM | 检查显存占用、报错阶段及队列自动重试记录；自动重试耗尽后交回 bridge 修复内存使用，记录实际配置变化并保持计划的实验口径。 |
| 超时或预算耗尽 | 区分单 job 超时与累计预算限制，报告已耗时、所处阶段及尚缺任务；续跑不会清空既有耗时。 |
| loss/指标出现 NaN、Inf 或发散 | 检查数据数值、归一化、损失和梯度相关日志，将实现问题交回 bridge；保留真实异常结果。 |
| 退出成功但产物缺失或无效 | 核对保存路径、指标字段、文件格式及后处理依赖；已有预测足够时补后处理，避免重复训练。 |
| job 等待或依赖阻塞 | 查看上游失败、GPU 占用、队列锁及配置限制，先处理根因；等待不记为模型性能失败。 |

对可修复问题交回 bridge 处理后继续执行；确实无法推进时说明具体错误、证据路径和缺少的条件。
方法性能不佳属于研究结果，不等于进程失败；不能篡改测试或伪造结果使其通过。

## 6. 中断续跑与交接

恢复时先核对已有 `running` 回执对应的进程和队列是否仍在执行；仍存活或状态未确认时先查清，避免重复启动。
已结束进程的中断状态由运行器恢复处理，保留历史回执和产物，不手动把失败或中断改成完成。

修复代码、配置或 manifest 后再次调用 `run_experiments()`。运行器复用身份匹配且产物校验通过的已完成 jobs，并按变更和依赖决定需要补跑的任务；无需删除整个结果目录或重做全部实验。

将以下执行证据交回 bridge，由其解释结果、核对完整计划并写结果报告：

- job ID、所属 D/B 块，以及已完成、失败、阻塞或仍在运行的状态。
- 实际设备、耗时、配置与计划有差异的部分。
- 关键日志、回执、指标、checkpoint 和预测等实际产物路径。
- 修复内容、续跑结果，以及尚未解决的问题及其证据。
