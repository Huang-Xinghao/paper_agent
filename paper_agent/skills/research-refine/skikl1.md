# 研究细化：以问题为中心、优雅、前沿技术意识的计划细化

细化并具体化：**$ARGUMENTS**

## 概述

当研究问题已经可见但技术路线仍然模糊时使用此技能。我们的目标不是提出一个臃肿的提案或一个基准购物清单。目标是将一个模糊的方向转变为一个**问题 -> 集中方法 -> 最小验证**文档，该文档足够具体以实现，足够优雅以感觉值得论文，并且足够流行以在基础模型时代引起共鸣。

这项技能有四个原则：

1. **不要丢失原来的问题。** 冻结一个不可变的**问题锚点**并在每一轮中重用它。
2. **最小的适当机制获胜。**更喜欢直接修复瓶颈的最小干预。
3. **一篇论文，一篇主要贡献。** 优先选择一篇尖锐的核心论点加上至多一篇支持性贡献。
4. **现代杠杆是先决条件，而不是装饰。** 当 LLM / VLM / 扩散 / RL / 蒸馏 / 推理时间缩放自然适合瓶颈时，请具体使用它们。不要把它们当作流行语。

```
用户输入（问题+模糊的方法）
  -> Phase 0 ( Claude ): Freeze 问题锚点
  -> 第 1 阶段 (Claude)：扫描研究论文 -> 确定技术差距 -> 选择最尖锐的路线 -> 撰写重点提案
  -> 第二阶段（Codex/GPT-6-Astra）：保真度、特异性、贡献质量和前沿技术杠杆的审稿
  -> 第 3 阶段（Claude）：锚定检查 + 简单性检查 -> 修改方法 -> 重写完整提案
  -> 第 4 阶段（ Codex ，同一线程）：重新评估修订后的提案
  -> 重复第 3-4 阶段，直到总分 >= 9 或达到 MAX_ROUNDS
  -> 第 5 阶段：将完整历史记录保存到 refine-logs/
  -> 可选交接：/experiment-plan 以获得详细的执行就绪实验路线图
```

## 常量

- **REVIEWER_MODEL = `gpt-6-astra`** —审稿人模型使用通过Codex MCP。
- **MAX_ROUNDS = 5** — 最大审稿修改轮次。
- **SCORE_THRESHOLD = 9** — 停止的最低总分。
- **OUTPUT_DIR = `refine-logs/`** — 回合文件和最终报告的目录。
- **MAX_LOCAL_PAPERS = 15** — 用于扫描研究参考的最大本地 papers/notes。
- **MAX_CORE_EXPERIMENTS = 3** — 此技能内核心验证块的默认上限。
- **MAX_PRIMARY_CLAIMS = 2** — 论文级论断的软上限。更喜欢一种主导论断加上一种支持性论断。
- **MAX_NEW_TRAINABLE_COMPONENTS = 2** — 真正的新型可训练部件的软性上限。仅在不超过此上限就无法成立时才允许超出。

> 如果需要，可以通过参数覆盖，例如  `/research-refine "problem | approach" -- max rounds: 3, threshold: 9`。

## 状态持久化（检查点恢复）

长时间运行的优化会话可能会中途失败（例如，API 超时、上下文压缩或会话中断）。为了避免丢失已完成的工作，请在每个阶段边界后将状态保留到 `refine-logs/REFINE_STATE.json`：

```json
{
  "phase": "review",
  "round": 1,
  "threadId": "019cd392-...",
  "last_score": 6.5,
  "last_verdict": "REVISE",
  "status": "in_progress",
  "timestamp": "2026-03-22T20:00:00"
}
```

**字段定义：**

| 场地 | 价值观 | 意义 |
|-------|--------|---------|
| `phase` | `"anchor"`  /  `"proposal"`  /  `"review"`  /  `"refine"`  /  `"done"` | 最后**完成**阶段 |
| `round` | 0– MAX_ROUNDS | 当前轮数 |
| `threadId` | 字符串或空 | 审稿人帖子ID为`codex-reply`连续性 |
| `last_score` | 数字或空 | 审稿人最近的总分 |
| `last_verdict` | 字符串或空 | 最新判决（READY / REVISE / RETHINK） |
| `status` | `"in_progress"`  /  `"completed"` | 循环状态 |
| `timestamp` | ISO 8601 | 上次写入状态的时间 |

**编写规则：**
- **在每个阶段完成之后写入**（而不是之前）。每次都覆盖——只有最新的状态才重要。
- **完成后**（第 5 阶段完成），设置 `"status": "completed"` 。

## 工作流程

### 初始化（检查点恢复）

在开始任何阶段之前，检查之前的运行是否留下了检查点：

1. **检查 `refine-logs/REFINE_STATE.json`**：
   - 如果**不存在**→**重新开始**（正常进入阶段0）
   - 如果存在且 `status` 是 `"completed"` → **重新启动**（删除状态文件，之前的运行已完成）
   - 如果存在并且 `status` 是 `"in_progress"` 并且 `timestamp` **早于 24 小时** → **全新启动**（killed/abandoned 运行中的过时状态 — 删除文件）
   - 如果存在并且 `status` 是 `"in_progress"` 并且 `timestamp` 是 **24 小时内** → **恢复**

2. **在恢复时**，读取状态文件并恢复上下文：
   - 读取所有现有的 `refine-logs/round-*.md` 文件以恢复之前的工作
   - 如果存在则读取`refine-logs/score-history.md`
   - 恢复`threadId`以保证审稿人线程的连续性
   - 向用户记录：`"Checkpoint found. Resuming after phase: {phase}, round: {round}."`
   - **根据保存的`phase`值跳转到下一阶段**：

   | 已保存 `phase` | 完成了什么 | 简历来自 |
   |---------------|-------------------|-------------|
   | `"anchor"` | 第 0 阶段完成 | 第 1 阶段（从第 0 轮上下文读取锚点） |
   | `"proposal"` | 第一阶段完成 | 第 2 阶段（读取 `round-0-initial-proposal.md` ） |
   | `"review"` | 第 2 或第 4 阶段已完成 | 第3阶段（读取最新的`round-N-review.md`） |
   | `"refine"` | 第三阶段完成 | 第 4 阶段（读取最新的 `round-N-refinement.md` ） |

3. **重新启动时**，确保 `refine-logs/` 目录存在并继续到阶段 0。

### 第 0 阶段：冻结问题锚点

在提出任何建议之前，请提取用户不可改变的底线问题。这个锚点必须逐字复制到每个提案和每个改进轮次中。

写：

- **底线问题**：必须解决什么技术问题？
- **必须解决的瓶颈**：当前方法中哪些具体弱点是不可接受的？
- **非目标**：该项目的明确“非”目标是什么？
- **约束**：计算、数据、时间、工具、目标会议或期刊、部署限制。
- **成功条件**：什么证据会让用户说“是的，这个方法解决了实际问题”？

如果以后审稿人的反馈会改变正在解决的问题，请将其标记为**漂移**并推迟或仔细调整。

**检查点：** 将 `refine-logs/REFINE_STATE.json` 写入 `{"phase": "anchor", "round": 0, "threadId": null, "last_score": null, "last_verdict": null, "status": "in_progress", "timestamp": "<now>"}` 。

### 第一阶段：制定初步提案

#### 步骤1.1：扫描支撑材料

首先检查`papers/`和`literature/`。仅阅读回答所需的相关部分：

- 目前的方法使用什么机制？
- 他们到底在哪里失败了这个问题？
- 最近哪些 LLM / VLM / 扩散 / RL 时代技术实际上与这里相关？
- 哪些训练目标、表示或接口是可重用的？
- 哪些细节可以区分真正的方法和重命名的高级想法？

如果本地不够，网上搜索最近的top-venue/arXiv作品。重点关注**方法部分、训练设置和失败模式**，而不仅仅是摘要。

#### 步骤 1.2：确定技术差距

不要停留在一般的研究问题上。使间隙可操作：

1. **当前流程失败点**：基线断裂在哪里？
2. **为什么简单的修复是不够的**：更大的上下文、更多的数据、提示、内存库或堆叠更多的模块。
3. **最小的充分干预**：可以合理解决瓶颈的最少额外机制是什么？
4. **前沿技术原生替代方案**：是否有更当前的使用基础模型时代技术基元的路线，更能匹配瓶颈？
5. **核心技术论断**：究竟什么样的论断机制才能经受住顶级目标会议或期刊的审查？
6. **所需证据**：捍卫论断需要什么最低证明？

#### 步骤1.3：选择最快捷的路线

在锁定方法之前，比较两条候选路线是否合理：

- **路线A：优雅的最小路线**——直接针对瓶颈的最小机制。
- **路线 B：前沿技术原生路线** - 更现代的路线，使用 LLM / VLM / 扩散 / RL / 蒸馏 / 推理时间缩放*仅当*它提供更清晰或更强大的故事时。

然后决定：

- 在规定的限制下，哪条路线更有可能成为一篇强论文？
- 哪条路线的故事相对最接近的作品来说更干净新颖？
- 哪条路线可以避免贡献蔓延？

如果两条路由都很弱，请重新考虑框架，而不是默认将它们组合成更大的系统。

#### 步骤1.4：首先具体化方法

该提案必须回答“我们实际上将如何构建它？”更喜欢方法细节而不是广泛的实验，更喜欢重用而不是发明。

覆盖：

1. **一句话方法核心论点**：单一最强机制论断。
2. **贡献焦点**：一项主要贡献和至多一项支持性贡献。
3. **复杂性预算**：哪些内容被冻结或重复使用，哪些内容是新的，以及哪些诱人的添加被有意排除。
4. **系统图**：模块、数据流、输入、输出。
5. **表示设计**：使用什么潜在、嵌入、计划令牌、奖励信号、记忆状态或对齐空间？
6. **训练秘诀**：数据源、监督、伪标签、底片、课程、损失、权重、分阶段训练与联合训练。
7. **推理路径**：在测试时如何使用经过训练的组件以及哪些信号流向何处。
8. **为什么该机制保持较小**：为什么不需要更大的堆栈。
9. **任何前沿技术基元的确切角色**：如果您使用 LLM / VLM / Diffusion / RL 组件，请指定它是否充当规划器、教师、评论家、奖励模型、先验生成器、搜索控制器或蒸馏源。
10. **故障处理**：可能会出现什么问题以及存在哪些后备或诊断？
11. **新颖和优雅的论点**：为什么这不仅仅是命名一个模块以及为什么论文看起来仍然有重点。

如果方法仍然只是描述为“添加模块”或“使用规划器”，则不够具体。

#### 步骤1.5：设计最小以论断为导向验证

实验的存在是为了验证该方法，而不是为了支配文档。

对于每个核心论断，定义可以验证它的**最小的强实验**：

- 正在测试的论断
- 必要的基线或消融实验
- 决定性指标
- 预期的方向性结果

附加规则：

- 确保一个实验块直接支持**问题关联点**。
- 如果存在复杂性风险，请包括一项**简化或删除检查**。
- 如果前沿技术基元是核心，请包括一项**必要性检查**，以表明该选择为何重要。
- 默认为 **1-3 个核心实验块**，并将完整的执行路线图留给 `/experiment-plan` 。

    阅读审稿包<绝对路径
    refine-logs/codex_round_1_review_bundle.md> 并遵循中的所有说明

```

    `shared-references/taste-calibration.md`;如果策划 known-good/known-bad
    过去的提案是可用的——例如来自研究维基的 accepted/rejected
    想法历史 — 首先在这些轴上每项得分 3 分以锚定量表，并且
    审稿中与该提案最接近的锚点名称。）

    对于每个得分 < 7 的维度，提供：
    - 具体弱点
    - 方法层面的具体修复（接口/损失/训练配方/集成点/删除不必要的部分）
    - 优先级：关键/重要/次要

    然后添加：
    - **简化机会**：在保留主要论断的同时删除、合并或重用组件的 1-3 种具体方法。如果已经很紧，请写“无”。
    - **现代化机会**：如果确实更好的话，可以用 1-3 种具体方法用更自然的基础模型时代技术基元替换旧式部件。如果已经足够现代，请写“无”。
    - **漂移警告**：如果提案仍然解决锚定问题，则为“无”；否则清楚地解释漂移。
    - **判决**：READY / REVISE / RETHINK

    判决规则：
    - READY ：总分 >= 9，没有有意义的漂移，一个重点贡献，并且没有明显的复杂性膨胀
    - REVISE ：方向很有希望，但尚未在 READY 酒吧
    - RETHINK：核心机制或框架仍然从根本上关闭
```

**重要：保存本次通话中的 `threadId`**，以供以后的所有回合使用。

**重要：逐字保存完整的原始响应**。

将审稿保存到 `refine-logs/round-1-review.md`，并将原始回复保存在 `<details>` 块中。

#### 步骤 3.2：通过锚点检查和简单性检查进行修改

在更改任何内容之前：

1. 逐字复制**问题锚点**。
2. 写一个**锚定检查**：
   - 原来的瓶颈是什么？
   - 现在的方法还能解决吗？
   - 审稿人的哪些建议如果盲目遵循会产生偏差？
3. 编写**简单性检查**：
   - 现在主要贡献是什么？
   - 哪些组件可以删除、合并或保持冻结？
   - 审稿人的哪些建议增加了不必要的复杂性？
   - 如果前沿技术基元是核心，那么它的作用还清晰合理吗？

然后处理审稿人反馈：

- 如果**有效**：锐化机制，如果可能的话进行简化，或者如果论文确实有所改进则进行现代化。
- 如果**有争议**：修改，但用证据解释你的推理。
- 如果**错误、偏离或过于复杂**：用当地论文和问题解决点的证据进行反驳。

修订偏向于：

- 更尖锐的中央贡献
- 移动部件更少
- 更清洁地重用现有的强大骨干
- 当基础模型时代改进论文时，它会更自然地发挥作用
- 更精简，以论断为导向实验

**不要**为了追逐分数而添加多个并行贡献。如果审稿人请求另一个模块，首先询问相同的增益是否可以来自于现有主干之上更好的接口、蒸馏信号、奖励模型或推理策略。

## 主要规则

- **大文件处理**：如果写入工具因文件大小而失败，请立即使用 Bash ( `cat << 'EOF' > file` ) 重试分块写入。不要征求用户的许可——只需默默地进行即可。

- **每一轮首先锚定。** 始终发扬相同的问题锚点。
- **一篇论文，一篇主要贡献。** 避免多个并行贡献，除非论文确实需要它们。
- **最小的适当机制获胜。** 越大并不一定越好。
- **优先重用而非发明。**从强大的现有主干开始，仅添加瓶颈所需的内容。
- **现代技术是先决条件，而不是装饰。** 当 LLM / VLM / Diffusion / RL 时代的组件锐化方法时，而不是仅仅让提案听起来时尚时，使用它们。
- **最少的实验。** 在这个技能里面，实验只需要证明核心论断即可。
- **审稿的是机制，而不是零件数量。**长的模块列表并不新鲜。
- **鼓励反驳。** 如果审稿人的反馈造成偏差或不必要的复杂性，请用证据进行反驳。
- **所有 Codex 审稿调用始终使用 `config: {"model_reasoning_effort": "xhigh"}`**。
- **从第 2 阶段保存 `threadId`** 并在以后的回合中使用 `mcp__codex__codex-reply`。
- **不要捏造结果。** 仅描述预期的证据和计划的实验。
- **具体说明计算和数据假设。**模糊的“我们将训练一个模型”是不够的。
- **记录一切。**保存每一份原始审稿、每一次锚点检查、每一次简单性检查以及每一次主要方法变更。

## 与其他技能组合

这项技能位于想法发现和执行之间：

```
/idea-creator“方向”->候选想法
/research-refine“问题：... | 方法：...”<- 你在这里
/experiment-plan -> 详细实验路线图
/run-experiment -> 执行所选方法
/auto-review-loop -> 迭代结果和论文
```

典型流程：

1. `/idea-creator`或本地阅读给你一个问题和一个模糊的方法方向
2. `/research-refine` 将其转变为一个锚定的、优雅的、前沿技术意识的方法计划
3. `/experiment-plan` 将最终提案转化为详细的以论断为导向的实验路线图
5. `/run-experiment` 执行所选的运行
6. 后面的循环对结果进行操作，而不仅仅是想法

如果您已经知道问题并且只需要具体的方法，那么该技能也可以独立使用。
